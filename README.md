## 문제

> **돌봄 중에는 기록할 수 없어서, 한 번 말한 정보가 기록·담당자·처리 확인까지 이어지지 않는다.**

주간보호센터는 하루 20~30명의 어르신을 요양보호사·간호조무사·사회복지사·운전원이 함께 돌본다.
그런데 돌봄 중에는 컴퓨터 앞에 앉을 수 없다. 그래서 한 사람의 특이사항이 이렇게 흩어진다.

```
종이 체크표  ·  전산(ERP)  ·  업무일지  ·  단톡방  ·  개인 메모
```

저희가 만난 주간보호센터 근무자는 이 흩어진 기록을 하원 후에 몰아서 다시 옮겨 적는 데
**하루 30~40분**을 쓴다고 답했다. 그리고 정보가 흩어지면 두 가지가 새어 나간다.

**전달이 끊긴다.** 보호자가 등원 차량 운전원에게 "어젯밤 잠을 못 주무셨다"고 말했지만
그 내용이 간호조무사까지 가지 않았고, 어르신이 오전 내내 조는 것을 보고서야 알게 된 일이 있었다.

**처리 여부를 모른다.** 보호자 연락·투약 확인·준비물 같은 후속 업무는 단톡방이나 메모에 남기지만,
완료 표시가 늦으면 담당자에게 다시 물어봐야 한다.

그리고 이 정보에는 **투약 시간, 낙상 위험, 이동 시 부축**처럼 어르신의 안전과 직결된 내용이 섞여 있다.

<sub>※ 위 수치는 저희가 만난 근무자의 응답과 체감 추정치입니다. 업계 통계가 아닙니다.</sub>

## 왜 지금인가

병원에서는 인수인계 AI가 이미 투자와 기술이전까지 진행됐다.
그런데 **인력난이 더 심각한 요양 현장에는 아무도 들어가지 않았다.**

기존 장기요양 전산은 공단 청구와 평가 대비에 맞춰져 있다.
그래서 기록을 **저장**하는 데서 멈추고, **다음 사람의 행동**으로 연결하지 않는다.

---

## 해결

이어봄은 이미 말로 하고 있는 인계를 그대로 받아, 다음 사람의 행동까지 잇는다.

```
① 한 번 남기기 → ② 어르신 카드 → ③ 담당자·기한 배정 → ④ 미처리/완료 추적 → ⑤ 문구 복사
```

| | 기능 | 하는 일 |
|---|---|---|
| **①** | **한 번 남기기** | 음성 · 짧은 텍스트 · 체크 중 편한 방식으로 한 번만 남긴다. 음성은 필수가 아니라 선택지 중 하나다. |
| **②** | **어르신 카드** | 여러 어르신이 뒤섞인 한 덩어리 발화를 어르신별로 나누고 **대상 · 시간 · 변화 · 조치 · 다음 행동**으로 정리한다. |
| **③** | **담당자 · 기한 배정** | 다음 행동이 어느 직종의 일인지, 언제까지 해야 하는지 추론해 붙인다. 투약 확인은 간호조무사, 보호자 연락은 사회복지사, 등하원은 운전원. 기한은 **당일 시각**이고 상한은 하원 시각이다. |
| **④** | **미처리 / 완료 추적** | 누가 무엇을 아직 안 했는지 한 화면에서 보인다. 확인한 사람이 대신 눌러도 되므로 전원이 앱을 깔 필요가 없다. |
| **⑤** | **문구 복사** | 기존 전산에 그대로 붙여넣을 **전산 기록 문구**와, 보호자에게 전할 **전달 문구**를 만들어 준다. 둘 다 직원이 검토한 뒤 직접 복사한다. |

## AI가 하는 일 / 절대 안 하는 일

| ✅ 하는 일 | ⛔ 안 하는 일 |
|---|---|
| 뒤섞인 발화를 **어르신별로 분리** | 의료적 판단 · 진단 · 투약 권고 |
| 한 문장에서 **상태 / 조치 / 다음 행동** 구분 | **없는 정보를 지어내기** |
| 다음 행동의 **담당 직종 추론** | 직원 검토 없이 보호자에게 자동 발송 |
| 안전 관련 항목(낙상·발열·투약 변경) **상단 배치** | 상시 녹음 |

> 안전 항목은 **지정 키워드로 자동 판정하거나 직원이 직접 표시**하며, 둘 중 하나만 걸려도 상단에 올린다.

> **근거 원문이 없으면 항목을 만들지 않는다.**
> 카드의 모든 항목에는 그 항목이 나온 원문 문장이 함께 표시된다.
> AI가 지어낸 할 일이 어르신 투약에 반영되면 그건 사고이기 때문이다.

## 포지셔닝

> **우리는 새 기록을 요구하지 않는다. 이미 말로 하고 있는 인계를 잡아서, 나머지 채널을 줄인다.**

- **대체하는 것** — 단톡방, 개인 메모, 종이 인계장
- **대체하지 않는 것** — 케어포 등 기존 장기요양 전산. 공단 청구·평가 대비는 그대로 둔다

즉 이어봄은 **기존 ERP를 대체하는 제품이 아니라, 그 앞단의 인수인계 레이어**다.
채널을 하나 더 만드는 게 아니라 셋을 없앤다.

수익 구조도 이 위치에서 나온다. 대체가 아니라 애드온이므로 **기존 전산 요금을 넘지 않는
시설당 월 정액 구독**으로 간다. 기존 전산이 주야간보호 기준 시설당 월 3.3만~4.5만원이고,
기본안은 **월 24,900원**이다.

<sub>※ 이 금액은 팀 제안값입니다. 시설장·센터장 인터뷰로 추가 지불 이유를 검증하기 전까지 확정이 아닙니다.</sub>

## 기술 스택

| 영역 | 선택 | 이유 |
|---|---|---|
| 프론트엔드 | React + TypeScript + Vite | 현장 입력과 관리자 화면을 반응형 웹 하나로 |
| 스타일 | Tailwind CSS | 큰 버튼·큰 글씨의 고령 친화 UI를 빠르게 |
| 서버 상태 | TanStack Query | 카드 목록·미처리 업무·완료 상태 갱신 |
| 백엔드 | Java 21 + Spring Boot 4.1.0 | REST API, AI 호출, 업무 상태 관리 |
| ORM / DB | Spring Data JPA + MySQL 8.4 LTS | 로컬과 배포 DB 통일 |
| 마이그레이션 | Flyway | 팀원·배포 환경에 동일한 스키마 적용 |
| AI | LLM API + Function Calling (JSON Schema 강제) | 정해진 필드 밖의 값을 애초에 못 만들게 하고 발화를 카드·업무 초안으로 구조화 |
| 음성 | Web Speech API / STT | 보조 입력. 텍스트·체크가 기본 대체 경로 |
