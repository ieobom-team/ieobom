# propose-change

**명세를 조용히 바꾸지 않기 위한 절차다.** 구현 중 현실과 명세가 어긋나면 여기서 멈춘다.

## 언제 쓰나

- Manyfast 명세대로 구현하면 기술적으로 불가능하거나 데모 일정 안에 못 끝낼 때
- 명세에 없는 사용자 동작·상태 규칙·예외를 결정해야 할 때
- API/JSON/DB 계약을 명세와 다르게 가져가야 할 때
- 구현하다 보니 명세 자체가 현장(인터뷰)과 안 맞는다는 게 드러났을 때

## 절차

1. **기존 Manyfast 요구사항**과 **발견한 제약**을 나란히 놓고 비교한다.
2. 기존대로 구현할 때의 위험을 구체적으로 적는다. "어렵다"가 아니라 무엇이 어떻게 깨지는지.
3. **대안을 최소 3개** 제시한다. 각각에 대해:
   - 무엇을 바꾸는가
   - MVP 범위와 데모 흐름에 미치는 영향
   - 남는 위험
4. **권장안 하나**를 고르고 이유를 적는다.
5. 승인 전에는 **Manyfast · Issue · 코드를 수정하지 않는다.**

## 승인 후

6. **Manyfast를 먼저 갱신하고 버전을 저장한다.**
7. 이어서 Issue 완료 조건 → 코드 → `docs/`를 같은 변경 흐름으로 갱신한다.

## 주의

- MVP 범위를 **넓히는** 변경은 PRD/Requirement 변경과 팀 승인을 거친다.
  기능을 더 붙이자는 방향이면 먼저 "핵심 기능이 실제 배포되어 작동하는가"를 기준으로 자른다.
- 명세를 바꾸는 게 아니라 **이번 Issue에서 안 하기로** 하는 선택도 유효한 대안이다.
  그 경우 Backlog Issue로 분리한다.
