# sync-manyfast

Notion(논의)과 코드(구현) 사이에서 **Manyfast를 최신 상태로 유지한다.**

## 절차

1. 입력 자료(Notion 회의록, 인터뷰, PR 결과)에서 **확정 사항 / 가설 / 미결정**을 분리한다.
   - 확정 사항만 반영 대상이다.
   - 가설과 미결정은 Manyfast **질문**으로 남긴다. 추측해서 채우지 않는다.
2. Manyfast에 이미 있는 **PRD · Requirement · Feature · Spec**을 확인한다.
   메타를 먼저 읽고 필요한 항목만 좁혀 읽는다.
3. **중복 생성 대신 기존 항목 업데이트 또는 하위 Spec 추가를 우선한다.**
4. 반영 대상은 **사용자 동작 · 정책 · 데이터 계약이 바뀌는 내용**으로 한정한다.
   제품 범위 · 타겟 · 리스크가 바뀌면 **PRD의 해당 섹션도 대상이다.** PRD는 섹션 단위로 갱신한다.
   내부 리팩터링, 파일 이동, 스타일 수정은 Manyfast를 건드리지 않는다.
5. **유저플로우 · 와이어프레임이 명세와 어긋나면 고치지 말고 보고만 한다.**
   쓰기 도구가 없어 에이전트는 수정할 수 없다. 어긋난 노드 ID · 페이지 ID와 고칠 방향을 적어
   사람이 Manyfast 웹에서 처리하도록 넘긴다.
6. 반영 전에 아래를 제시한다.
   - 변경 요약
   - 대상 항목 (ID)
   - 영향받는 Issue
   - 저장할 버전 이름
   - **사람이 웹에서 직접 고쳐야 할 유저플로우 · 와이어프레임 항목**
7. **승인 후** Manyfast를 갱신한다. 에이전트 수정분은 제안 상태이므로 **사람이 Manyfast 웹에서 검토·승인(확정)한 것을 확인한 뒤** 버전을 저장한다.
8. Notion에는 **기본적으로 아무것도 쓰지 않는다.**
   결정의 배경(왜)은 Manyfast Feature의 `rationale`에 담는다.
   회의록에 반영 사실을 남길지는 사람이 판단하며, 요청받았을 때만 한 줄로 남긴다.

## 버전 규칙

- **첫 Issue를 만들기 전에 이름 있는 버전이 하나는 있어야 한다.**
  Issue template의 "기준 버전"이 필수 항목이라, 자동 저장(`v1`, `v2`)만 있으면 Issue를 만들 수 없다.
- **자동 저장된 버전에는 나중에 이름을 붙일 수 없다.** 변경이 있는 시점에 이름과 함께 저장한다.
  변경 없이 저장을 시도하면 `no_changes`로 거부된다. Manyfast는 웹에서 편집할 때마다 자동으로 버전을 찍으므로,
  이름 붙일 버전은 **명세를 갱신하는 그 순간**에 저장한다.
- P0 기능 구현 시작 전 `v0.1-core-flow`를 저장한다.
- 데모 흐름 또는 사용자 동작이 바뀌면 다음 버전을 저장한다.
- 단순 문구 수정이나 내부 구현 변경만으로는 버전을 저장하지 않는다.
- 저장한 버전 이름은 관련 Issue와 PR에 기록한다.

## 경계

- Notion 회의록을 그대로 명세로 옮기지 않는다. **확정 여부를 먼저 가른다.**
- Manyfast 원문을 `docs/`에 복제하지 않는다. `docs/contracts/`에는 코드와 함께 바뀌는 기술 계약만 둔다.
- **유저플로우 · 와이어프레임을 에이전트가 고치려 하지 않는다.** 읽기 전용이다.
