# export API

검토 완료 카드에서 만드는 **전산 기록 문구**와 **보호자 전달 문구**, 그것을 어르신 단위로 이어 붙인 **당일 묶음**,
그리고 이 둘을 파일로 내려받는 길과 **어르신 당일 인계 항목 표**.

- Manyfast: `R-TUBGKD` 기록 및 보호자 전달 문구 출력 / `F-GUSOFG` 기록 및 보호자 전달 문구 복사
- 가명처리 규칙은 `R-LIEATL` / `F-LUDCWW` rules 에서 온다
- 기준 버전: `v0.4-export-file-0814` (파일 출력 밖의 항목은 `v0.3-plan-0813`에서 바뀌지 않았다)
- 관련 화면: 유저플로우 "AI 인계 도구 내비게이션 맵" — n36 기록 문구 출력 화면 → n37 전산 기록 문구 / n38 보호자 전달 문구 / n62 어르신 당일 묶음 문구 → n39 문구 수정 → n40 문구 복사 / n41 파일 다운로드

> 제품이 **왜** 이렇게 동작하는지는 Manyfast가 기준이다. 여기에는 **JSON이 어떻게 생겼는지**만 적는다.

---

## 흐름

```
PATCH /api/handover-cards/{id}/review-status   검토 완료로 올린다 (handover-card-schema.md)
      ↓                                        여기서부터 exportAllowed 가 참이 된다
POST  /api/handover-cards/{id}/exports         두 문구 생성. 이미 있으면 그대로 돌려준다
      ↓
PUT   /api/exports/{phraseId}                  직원이 검토하며 고친 문구
POST  /api/exports/{phraseId}/copy             직원이 복사했다는 사실

GET   /api/care-recipients/{id}/export-bundles       어르신 당일 묶음. 읽을 때 만든다
POST  /api/care-recipients/{id}/export-bundles/copy  묶음을 복사했다는 사실

GET   /api/exports/{phraseId}/file                        같은 문구를 파일로
GET   /api/care-recipients/{id}/export-bundles/file       같은 묶음을 파일로
GET   /api/care-recipients/{id}/export-sheet              어르신 당일 인계 항목 표. 단위가 다르다
```

**보내는 엔드포인트는 없다.** 만들고, 고치고, 복사한 사실을 남기는 것이 전부다.
보호자 자동 발송과 ERP 연동은 MVP 범위 밖이고, 범위 문제이기 이전에 **검토를 거치지 않은 문구가
나가지 않게 하는 장치**다. 문구를 실제로 옮기는 것은 직원의 복사·붙여넣기다.

## 출력이 두 종류인 이유

같은 사실을 담아도 읽는 사람이 다르다.

| 유형 | 읽는 사람 | 말투 | 길이 상한 |
|---|---|---|---|
| `RECORD` 전산 기록 문구 | 장기요양 전산에 붙여넣는 직원 | 기록체 (`~함` `~하심`) | 300자 |
| `GUARDIAN` 보호자 전달 문구 | 보호자 | 존댓말, 짧고 담담하게 | 200자 |

**말투와 길이는 Manyfast에서 확정된 값이다.** (`F-GUSOFG` rules · display, `v0.3-plan-0813`)
구현은 `com.ieobom.api.ai.ExportPhraseSchema`의 프롬프트로 이 값을 지킨다. **여기 적힌 값을 고치려면
Manyfast를 먼저 고친다.**

말투가 명세에 올라가 있는 이유는 그것이 표현 취향이 아니라 **안전 정책**이기 때문이다. 보호자 전달 문구에
증상의 원인을 추정하는 표현이나 불안을 키우고 안심시키는 표현을 넣지 않는다는 규칙은 "의료적 판단을 만들지
않는다"의 직접적인 연장이다. 프롬프트에만 있으면 누가 프롬프트를 고칠 때 정책이 조용히 바뀐다.

## 근거 없는 내용을 어떻게 막는가

구조화의 `CardDraftVerifier`처럼 **근거 원문과 글자를 대조할 수는 없다.**
문구는 다듬어진 서술형이라 원문에 그대로 존재하지 않는다. 대신 세 겹으로 막는다.

| 겹 | 어디서 | 무엇을 |
|---|---|---|
| 0. 가명처리 | `RecipientAliases` | 모델에 **어르신 실명을 주지 않는다.** 호출 앞에서 내부 ID로 바꾸고 응답을 받은 자리에서 되돌린다 |
| 1. 입력 차단 | `ExportInput` | 모델에 **인계 원문을 주지 않는다.** 검토 완료 카드 한 장의 내용만 준다 |
| 2. 스키마 강제 | `ExportPhraseSchema` | 두 문구 말고 다른 것을 만들 자리를 두지 않는다 (`strict` · `additionalProperties: false`) |
| 3. 서버 검증 | `ExportPhraseVerifier` | 그럼에도 카드에 없는 값이 문구에 나타났는지 본다 |

1번이 가장 중요하다. 원문에는 그 카드가 담기로 한 것 말고도 다른 어르신 이야기와 아직 검토되지 않은
내용이 섞여 있다. **주지 않은 사실은 문구에 들어갈 수 없다.**

0번은 근거가 아니라 개인정보 쪽 장치이고, 규칙과 한계는
[handover-card-schema.md의 가명처리](handover-card-schema.md#가명처리--실명은-llm-경계를-넘지-않는다)에 함께 적었다.
**어르신 칸뿐 아니라 상태·조치·근거 칸도 치환해서 보낸다.** 근거 원문은 인계 원문에서 잘라 온 구간이고
상태·조치 칸은 직원이 고칠 수 있어서, 어느 칸에나 이름이 섞일 수 있다.
**되돌리는 자리는 판정과 저장보다 앞이다.** 내부 ID인 채로 저장하면 ID 안의 숫자가 아래 "카드에 없는 숫자"로
잡히고, 직원이 화면(실명)에서 고쳐 저장한 문구만 실명이 되어 저장된 형식이 갈린다.

2번에서 "참고 사항" 같은 자유 서술 필드를 두지 않는 이유는, 그 자리가 있으면 의료적 판단이 그리로 들어오기
때문이다. 모델이 만들 수 있는 것은 두 문자열뿐이다.

### 서버 검증 — 무엇이 검토 안내를 다는가

| 판정 | 언제 | 결과 |
|---|---|---|
| 문구가 비었다 | 만들 때 · 고칠 때 | `text`가 `null`. **복사할 수 없다** |
| 문구에 **카드에 없는 숫자**가 있다 | 만들 때 · 고칠 때 | 안내를 단다. 문구는 남는다 |
| 문구에 **다른 어르신 이름**이 있다 | 만들 때 · 고칠 때 | 위와 같다 |
| 문구가 1000자를 넘는다 | 만들 때 · 고칠 때 | 잘라 저장하고 안내를 단다 |
| **문구를 만든 뒤 카드가 바뀌었다** | **읽을 때** | 안내를 단다. 문구는 남는다 |

숫자를 보는 이유는 **지어낸 사실이 대개 숫자로 나타나기** 때문이다. 체온, 횟수, 시각, 복용량이 그렇고
그중 무엇이든 카드에 없는 값이 보호자에게 나가면 그게 사고다. 문장이 다듬어져도 숫자는 다듬어지지 않으므로
이 대조는 서술형 문구에도 그대로 걸린다.

**걸렸다고 문구를 버리지 않는다.** 안내를 붙여 직원에게 넘긴다. 이 제품의 출력은 직원 검토와 직접 복사를
전제로 하므로, 서버가 조용히 지우면 직원은 무엇을 확인해야 하는지 모른 채 문구만 사라진 화면을 보게 된다.

#### 마지막 한 줄만 "읽을 때" 도는 이유

앞의 넷은 문구를 쓰는 순간의 판정이라 `review_notice`에 저장된다. 마지막은 저장할 수 없다.
**문구를 만든 뒤에도 카드는 고칠 수 있고**(`PUT /api/handover-cards/{id}`), 그때 `generated_text`는
만든 시점에 얼어붙은 채 남는다. 응답의 `evidenceText`는 카드에서 실시간으로 오므로, 화면에서 근거와 문구가
어긋난 채 **아무 신호 없이** 놓이게 된다.

그래서 응답의 `reviewNotice`·`needsReview`는 **저장된 값이 아니라 읽는 시점에 합성한 값**이다.
저장된 안내가 있으면 뒤에 이어 붙는다. 판정은 `ExportPhraseVerifier.reviewNoticeOf` 하나이고,
카드 단위 응답과 묶음이 같은 것을 쓴다.

| | |
|---|---|
| 기준 시각 | `export_phrase.verified_at` — 문구를 **만들거나 고친** 시점 |
| 바뀐 것으로 보는 조건 | `handover_card.updated_at`이 그보다 **뒤** |
| 해소하는 방법 | `PUT /api/exports/{phraseId}`로 문구를 고친다 |

**복사(`copied_at`)는 안내를 해소하지 않는다.** 그래서 기준 시각으로 `export_phrase.updated_at`을 쓰지
않고 `verified_at`을 따로 둔다. `updated_at`은 복사 기록을 남길 때도 올라가므로, 그것을 기준으로 삼으면
**직원이 복사하는 순간 경고가 조용히 사라진다.**

**카드의 `updated_at`은 검토 상태 전환과 안전 표시로도 올라간다.** 내용이 그대로인데 안내가 붙을 수 있다는
뜻이다. 좁히지 않고 두는 이유는 두 방향의 값이 다르기 때문이다 — 틀리게 붙으면 직원이 한 번 더 확인하고,
틀리게 빠지면 **근거와 어긋난 문구가 검토를 거친 얼굴로 보호자에게 나간다.**

**재생성 엔드포인트는 열지 않는다.** "직원이 고쳐 둔 문구를 덮어쓸 것인가"를 정해야 하는데 그 규칙이
Manyfast에 없다. 안내를 보고 `PUT`으로 고치는 길이 열려 있으므로 막히지 않는다.

## `POST /api/handover-cards/{cardId}/exports`

### 응답 — `201 Created` (새로 만들었을 때)

```json
{
  "cardId": 31,
  "needsReview": false,
  "phrases": [
    {
      "id": 7,
      "cardId": 31,
      "handoverId": 12,
      "careRecipientId": 1,
      "careRecipientName": "김말순",
      "phraseType": "RECORD",
      "phraseTypeLabel": "전산 기록 문구",
      "text": "12시 40분경 점심 식사량 저하 보이심. 죽으로 바꿔 드림.",
      "generatedText": "12시 40분경 점심 식사량 저하 보이심. 죽으로 바꿔 드림.",
      "edited": false,
      "needsReview": false,
      "reviewNotice": null,
      "evidenceText": "점심을 거의 안 드셨어요",
      "copiedAt": null,
      "createdAt": "2026-08-11T15:02:11.402"
    },
    {
      "id": 8,
      "phraseType": "GUARDIAN",
      "phraseTypeLabel": "보호자 전달 문구",
      "text": "점심 식사량이 줄어 죽으로 바꿔 드렸습니다.",
      "...": "위와 같은 모양"
    }
  ]
}
```

`phrases`는 **언제나 두 개**다. 한쪽이 만들어지지 못했어도 자리는 남고 `text`가 `null`이 된다.
화면이 "보호자 문구 칸이 아예 없는 상태"와 "문구를 못 만든 상태"를 구분하지 못하면 안 된다.

위 `phrases[]` 한 항목이 **문구 API가 공유하는 모양**이다. 아래 수정 · 복사도 같은 모양 하나를 돌려준다.

각 문구는 `cardId` · `handoverId` · `evidenceText`를 **자기 안에 들고 있다.** 문구 하나만 떼어 봐도
근거로 돌아갈 수 있어야 하기 때문이다. (Manyfast `R-TUBGKD` 수락기준 3) 문구만 돌려주면 화면이 근거를
보여 주려고 카드를 따로 불러야 하고, 그 호출을 빠뜨린 화면에서는 직원이 근거 없이 문구만 보고 복사하게 된다.

`needsReview`는 최상위에도 있다. 두 문구 중 하나라도 안내가 붙으면 참이다. 화면은 이 값 하나로 상단 안내를 띄운다.

### 응답 — `200 OK` (이미 만들어 둔 문구가 있을 때)

본문 모양은 같다. **모델을 다시 부르지 않는다.**

직원이 고쳐 놓은 문구를 새 호출이 덮어쓰면, 화면을 다시 열었다는 이유만으로 검토 결과가 사라진다.
그래서 이 엔드포인트는 "만들거나, 이미 있으면 그대로 준다"로 동작한다. 화면을 다시 열든 대시보드에서
곧장 들어오든(유저플로우 "새 플로우 3" n50 → n39) 같은 요청 하나면 된다.

**재생성은 제공하지 않는다.** 고칠 것은 아래 수정 API로 고친다.

그래서 **문구를 만든 뒤 카드를 고치면 문구가 옛 내용으로 남는다.** 검토 완료 카드도 수정할 수 있으므로
(어르신을 비우는 것만 막는다) 실제로 일어날 수 있는 경로다. 이 응답은 그때 `needsReview`를 참으로 올리고
`reviewNotice`로 알린다. ([서버 검증](#마지막-한-줄만-읽을-때-도는-이유)) 안내를 보고 아래 수정 API로 고치면
해소된다.

### 규칙

| 규칙 | 결과 |
|---|---|
| 카드가 없음 | `404` — `HANDOVER_CARD_NOT_FOUND` |
| 아직 `검토 필요` 카드 | `409` — `CARD_NOT_REVIEWED`. **모델을 부르지 않는다** |
| `LLM_API_KEY` 미설정 · 호출 실패 · 스키마에 맞지 않는 응답 | `503` — `LLM_UNAVAILABLE`. **문구를 하나도 만들지 않는다** |

검토 완료 판정은 **`HandoverCard.canGenerateExport()` 하나뿐이다.** 카드 목록의 `exportAllowed`와
같은 것을 본다. 조건이 두 군데에 있으면 한쪽만 고쳐진 채로 검토되지 않은 내용이 보호자에게 나갈 수 있다.
`409`의 `message`도 카드가 들고 있는 문장(`검토 완료 후 생성할 수 있습니다.`)을 그대로 쓴다.

어르신을 가리지 못한 카드는 애초에 검토 완료가 되지 못하므로,
**문구가 있는 카드에는 언제나 어르신이 있다.** ([handover-card-schema.md](handover-card-schema.md#patch-apihandover-cardsidreview-status))

## `PUT /api/exports/{phraseId}`

직원이 검토하며 고친 문구를 저장한다. (Manyfast `F-GUSOFG` action)

```json
{ "text": "점심 식사량 저하 보이심. 죽으로 바꿔 드림." }
```

응답은 `200 OK`와 고쳐진 문구 하나다.

**고칠 수 있는 것은 본문 하나뿐이다.** 유형과 연결 카드는 문구가 어디서 나왔는지를 말하는 값이라 요청으로
받지 않는다. 받을 수 있으면 전산 기록 문구를 보호자 문구로 바꿔치기하거나, 다른 어르신 카드에 문구를 옮겨
붙일 수 있다.

`generatedText`는 **건드리지 않는다.** AI가 원래 무엇을 만들었는지가 남아 있어야 "직원 검토를 거쳤다"를
나중에 말할 수 있다. 화면에 나가는 `text`는 고친 것이 있으면 그것이고, 없으면 `generatedText`다.

고친 문구도 **같은 기준으로 다시 본다.** 직원이 카드에 없는 내용을 적어 넣을 수도 있고, 반대로 AI 문구에
붙어 있던 안내가 수정으로 해소될 수도 있다.

**"문구를 만든 뒤 카드가 바뀌었다"는 안내도 여기서 해소된다.** 이 요청이 문구를 카드와 다시 대조하는
유일한 지점이기 때문이다. (`verified_at`이 갱신된다)

| 규칙 | 결과 |
|---|---|
| 문구가 없음 | `404` — `EXPORT_PHRASE_NOT_FOUND` |
| `text`가 비었거나 공백뿐 | `400` — `VALIDATION_FAILED` |

비워 보낼 수 없는 이유는 이것이 **지우는 동작이 아니라 고치는 동작**이기 때문이다.
문구를 지우고 싶으면 복사하지 않으면 된다.

## `POST /api/exports/{phraseId}/copy`

직원이 복사했다는 사실을 남긴다. (Manyfast `F-GUSOFG` outcome — 복사한 문구 유형과 복사 시점)

요청 본문이 없다. 응답은 `200 OK`와 `copiedAt`이 채워진 문구 하나다.

**문구를 어디로도 보내지 않는다.** 실제 복사는 화면이 하고, 이 요청은 그 사실을 남기는 것이 전부다.

| 규칙 | 결과 |
|---|---|
| 문구가 없음 | `404` — `EXPORT_PHRASE_NOT_FOUND` |
| 복사할 문구가 아직 없음 | `409` — `EXPORT_PHRASE_EMPTY` |

**검토 안내가 붙어 있어도 복사를 막지 않는다.** 안내는 "확인하고 쓰라"는 말이지 "쓰지 말라"는 말이 아니고,
최종 판단은 직원이 한다. 막는 것은 복사할 문구 자체가 없을 때뿐이다. 없는 것을 복사한 것으로 남길 수는 없다.

여러 번 복사하면 `copiedAt`이 마지막 시점으로 갱신된다. 복사 횟수를 세지 않는다.
지금 필요한 것은 "이 문구가 실제로 쓰였는가"이고, 몇 번 눌렸는지는 화면이 묻지 않는다.

## `GET /api/care-recipients/{careRecipientId}/export-bundles`

어르신 한 명의 **당일 검토 완료 문구를 유형별로 이어 붙인 묶음**. (Manyfast `F-GUSOFG` action)
`date`를 생략하면 오늘이다.

```json
{
  "careRecipientId": 1,
  "careRecipientName": "김말순",
  "date": "2026-08-12",
  "bundles": [
    {
      "phraseType": "RECORD",
      "phraseTypeLabel": "전산 기록 문구",
      "text": "복도에서 넘어지실 뻔해 부축해 드림.\n12시 40분경 점심 식사량 저하 보이심. 죽으로 바꿔 드림.",
      "empty": false,
      "phraseCount": 2,
      "needsReview": false,
      "notice": null,
      "phrases": ["...카드 단위 응답과 같은 모양"]
    },
    {
      "phraseType": "GUARDIAN",
      "...": "위와 같은 모양"
    }
  ]
}
```

`bundles`는 **언제나 두 개**다. 한쪽에 담을 문구가 없어도 자리는 남는다.
두 유형을 한 번에 내리는 이유는 화면이 둘을 나란히 보여 주기 때문이다. (`F-GUSOFG` display)

**묶음에는 식별자가 없다.** 저장하지 않기 때문이다. (`F-GUSOFG` dataSpec) 다시 가리키려면
어르신 · 날짜 · 유형으로 다시 부른다.

`phrases[]`는 카드 단위 응답과 같은 모양이라 항목마다 `cardId` · `handoverId` · `evidenceText`를
들고 있다. 묶어 놓아도 **문장 하나에서 근거로 돌아갈 수 있어야 한다.** (`R-TUBGKD` 수락기준 3)

### 왜 묶는가

카드 단위 복사만으로는 `R-TUBGKD` 수락기준 1의 "어르신별"이 실질로 충족되지 않는다.
어르신 1명에 카드가 4장이면 **복사 4번 · 붙여넣기 4번**이고, 붙여넣은 네 문장이 이어지지 않아
직원이 전산 안에서 다시 합치게 된다. 보호자 전달 문구는 더 나쁘다 — 4번 보내지 않으므로 직원이 손으로
합치는데, **그 편집은 검토를 거치지 않는다.**

**생성 단위는 그대로 카드 한 장이다.** 묶음은 저장하지 않고 읽을 때 만든다. 저장하면
"문구 하나 = 카드 하나 = 근거 하나"가 깨지고, 근거 연결이 1:N이 되면 그 문장이 원문 어디서 나왔는지
더 이상 말할 수 없다.

**이어 붙일 때 모델을 부르지 않는다.** 다시 다듬으면 근거가 1:N이 되고 호출 비용이 두 배가 된다.

### 무엇이 들어가고 어떤 순서로 붙는가

| 규칙 | 근거 |
|---|---|
| **검토 완료 카드의 문구만** 넣는다 | `F-GUSOFG` dataSpec |
| **안전 관련 항목의 문구를 먼저**, 그다음 **관찰 시각 순** | `F-GUSOFG` action |
| 같은 시각이거나 관찰 시각이 없으면 카드가 만들어진 순서 | 구현 |
| 문구 사이는 **줄바꿈 하나(`\n`)** | 구현 |

검토 완료 여부를 **읽는 시점에 다시 본다.** 문구를 만든 뒤에도 카드를 검토 필요로 되돌릴 수 있고,
그때 이미 만들어진 문구는 남아 있다. 조회에서 거르지 않으면 검토가 취소된 내용이 묶음에 섞인다.

안전 판정은 카드의 `safetyRelated`를 그대로 쓴다. 문구에는 안전 여부가 없다.
관찰 시각은 원문에서 뽑지 못하면 비어 있으므로 뒤로 보낸다.

**날짜 기준은 카드의 생성 시각**이다. 카드 목록(`GET /api/handover-cards?date=`)과 같은 기준이라야
화면에서 본 카드와 묶음의 구성이 어긋나지 않는다. 관찰 시각은 비어 있을 수 있어 기준으로 쓸 수 없다.

**구분자는 Manyfast에 없는 표시 수준의 값이라 구현에서 정했다.** 줄바꿈 하나인 이유는 전산 입력창과
보호자 메시지 양쪽에서 문장이 서로 붙어 버리지 않는 가장 약한 구분이기 때문이다. 화면([`#18`](https://github.com/ieobom-team/ieobom/issues/18))에서
문제가 되면 `propose-change`로 올린다.

**묶음에는 길이 상한을 두지 않는다.** 300자 · 200자는 `F-GUSOFG` display에서 **문구 하나**에 붙은
값이다. 묶음에 걸면 카드가 늘어날수록 뒷문구가 잘리는데, 그건 "어르신당 한 번 복사"를 도로 깨뜨린다.

### 묶음도 검토가 필요할 수 있다

| 판정 | `empty` | `needsReview` | `notice` |
|---|---|---|---|
| 그날 검토 완료 문구가 없다 | `true` | `false` | 검토 완료로 올리라고 안내 |
| 담을 글자가 없는 문구가 있다 | 나머지에 달림 | `true` | **몇 장이 빠졌는지** 안내 |
| 포함된 문구에 검토 안내가 붙어 있다 | `false` | `true` | 몇 개인지 안내 |

세 번째 줄은 **카드 단위 응답과 똑같이 판정한다.** 저장된 안내뿐 아니라 "문구를 만든 뒤 카드가 바뀌었다"도
여기서 세어진다. 두 판정이 갈라지면 카드별 화면에는 안내가 뜨는데 묶음 화면에서는 **같은 문구가 아무 표시
없이 복사된다.**

**담을 글자가 없는 문구는 묶음에서 뺀다.** 이어 붙일 수 없는 문구를 항목에 남겨 두면, 묶음을 복사했을 때
**실제로 복사되지 않은 문구에 복사 기록이 남는다.** 대신 몇 장이 빠졌는지 알려 직원이 모르고 넘어가지
않게 한다. 그 카드의 문구는 카드 단위 수정 API로 직접 쓰면 다음 조회부터 묶음에 들어온다.

`notice`가 하나뿐인 이유는 화면이 안내를 한 자리에 띄우기 때문이다. 빈 묶음 안내인지 검토 안내인지는
`empty`와 `needsReview`가 가른다.

### 규칙

| 규칙 | 결과 |
|---|---|
| 어르신이 목록에 없음 | `404` — `CARE_RECIPIENT_NOT_FOUND` |

**이 요청은 아무것도 저장하지 않는다.** 문구를 새로 만들지도 않는다.

## `POST /api/care-recipients/{careRecipientId}/export-bundles/copy`

직원이 묶음을 복사했다는 사실을 남긴다. (Manyfast `F-GUSOFG` outcome)

```json
{ "phraseType": "RECORD", "date": "2026-08-12" }
```

`date`를 생략하면 오늘이다. 응답은 `200 OK`와 **복사 시점이 채워진 묶음 하나**다.

**복사 기록은 묶음에 들어간 문구 하나하나에 남는다.** 묶음 자체가 저장 대상이 아니기 때문이다.
묶음에서 빠진 문구에는 아무것도 남지 않는다. 복사되지 않은 문구를 복사한 것으로 남길 수는 없다.

**복사할 문구의 식별자를 받지 않는다.** 서버가 조회와 같은 규칙으로 묶음을 다시 만들어 그 안의 문구에
기록을 남긴다. 클라이언트가 목록을 정하게 하면 화면이 보여 준 묶음과 복사 기록이 갈릴 수 있다.
대신 **유형은 받는다.** 무엇을 복사했는지는 서버가 알 수 없고, 그것이 남길 기록의 내용이다.

| 규칙 | 결과 |
|---|---|
| 어르신이 목록에 없음 | `404` — `CARE_RECIPIENT_NOT_FOUND` |
| `phraseType`이 없거나 정의되지 않은 값 | `400` — `VALIDATION_FAILED` |
| 묶음에 담을 문구가 없음 | `409` — `EXPORT_BUNDLE_EMPTY` |

단건 복사와 같은 이유로 **검토 안내가 붙어 있어도 막지 않는다.** 막는 것은 복사할 문구 자체가 없을 때뿐이다.

## 파일 내려받기

`GET /api/exports/{phraseId}/file?format=txt`
`GET /api/care-recipients/{id}/export-bundles/file?phraseType=RECORD&format=md&date=2026-08-14`

**내려받는 단위는 복사와 같다.** 카드 한 장의 문구 하나이거나 어르신 당일 묶음 하나다.
(Manyfast `F-GUSOFG` action) 화면에서 복사할 수 있는 것과 내려받을 수 있는 것이 갈리면 직원은 같은
자리에서 두 가지 다른 결과를 얻는다. 그래서 묶음 파일은 [`GET .../export-bundles`](#get-apicare-recipientscarerecipientidexport-bundles)와
**같은 규칙으로 다시 만든 묶음**을 그린다 — 무엇이 들어가고 어떤 순서로 붙는지를 여기서 다시 정하지 않는다.

**모델을 부르지 않는다.** 같은 구조화 결과의 다른 렌더링이고, 파일이 늘어도 담기는 사실은 늘지 않는다.

응답은 `200 OK`와 파일 바이트다. `Content-Disposition: attachment` 로 내려간다.

### 지금 있는 형식

| `format` | Content-Type | 무엇이 담기나 |
|---|---|---|
| `txt` | `text/plain;charset=UTF-8` | 본문 → 구분선 → 근거 → 고지 |
| `md` | `text/markdown;charset=UTF-8` | 제목·구획을 갖고, 근거를 문구와 **짝지어** 담는다 |
| `docx` | `application/vnd.openxmlformats-officedocument.wordprocessingml.document` | **검토용 서술형 기록 초안** — 제목 → 본문 → 근거 → 고지 |

**`xlsx`는 이 목록에 없다.** 담는 것이 문구가 아니라 카드와 후속 업무의 표라 단위가 다르고,
그래서 [엔드포인트가 따로 있다](#어르신-당일-표-내려받기). 문구 쪽 `format`으로 `xlsx`를 보내면
`400`이다 — 고를 수 있으면 렌더러가 없는 요청이 `500`으로 떨어진다.

**`docx`를 "일지"라고 부르지 않는다.** (`F-GUSOFG` action) 워드로 받은 문서에 그 이름이 붙으면 그대로
기관에 제출해도 되는 문서로 읽힌다. 이 파일이 하는 일은 담당자가 문장을 고쳐 기관 서식이나 전산에 옮기기
좋게 미리 늘어놓는 것까지다.

`txt`가 줄바꿈을 `\r\n`으로 쓰는 이유는 이 파일이 열리는 곳이 대부분 윈도우의 메모장과 전산
입력창이기 때문이다. `\n`만 쓰면 옛 편집기에서 한 줄로 뭉쳐 보이고, 그러면 붙여넣기용이라는 이 형식의
존재 이유가 사라진다.

### 파일에도 근거가 들어간다

**`R-TUBGKD` 수락기준 4가 문구뿐 아니라 파일에도 요구한다.** 파일만 건네받은 사람이 근거를 볼 수
없으면 그 사람에게는 검토할 방법이 없다.

`txt`에서 근거와 고지가 **구분선 아래**에 있는 이유는 붙여넣는 자리가 위쪽이기 때문이다. 본문 사이에
끼면 붙여넣을 때마다 지워야 한다. 그렇다고 빼지는 않는다.

### 고지

모든 파일에 아래 한 줄이 들어간다. (Manyfast `F-GUSOFG` display, `ExportDocument.DISCLAIMER`)
문구 파일에서는 끝줄이고, **표에서는 맨 윗줄이다** — 표는 행이 늘어날수록 아래가 화면 밖으로 밀린다.

> 이 파일은 담당자 검토를 전제로 만든 기록·전달 초안입니다. 기관 서식이나 전산에 옮기기 전에 사실관계를 확인해 주세요.

**법률 표현을 쓰지 않는다.** 법률 자문을 받은 적이 없으므로 "법정 서식을 대체하지 않는다" 같은 단정 대신
"옮기기 전에 확인해 달라"까지만 말한다. 같은 이유로 어느 기관의 어떤 양식에 맞는다고도 말하지 않는다.
그 양식을 한 번도 본 적이 없다. (`F-GUSOFG` rules)

### 파일 이름

`이어봄_전산기록문구_김말순_2026-08-14.txt`

한글이라 헤더에는 RFC 5987 `filename*=UTF-8''…` 로 인코딩해 나간다. 손으로 만들면 브라우저마다 다르게
읽어 이름이 깨진다. **프론트와 API는 같은 출처라**([`architecture.md`](../architecture.md#배포-배치))
화면이 CORS 설정 없이 이 헤더를 그대로 읽는다.

**어르신을 내부 ID로 적지 않는다.** 가명처리는 LLM 경계에서만 일어나고, 이 파일은 직원이 자기 PC에서
찾아 쓰는 것이다. `IB-009`로 적으면 여러 개를 받아 둔 직원이 어느 것이 누구 것인지 알 수 없다.
파일 안에는 어차피 실명과 상태 이야기가 들어 있으므로 이름에 실명을 쓴다고 새로 드러나는 것은 없다.

### 무엇이 남는가

**형식과 시점만 남긴다.** (`F-GUSOFG` dataSpec) 파일은 저장하지 않는다 — 같은 구조화 결과를 다시 그린
것이라 보관할 이유가 없고, 보관하면 어르신의 건강 상태가 담긴 파일이 서버에 쌓인다.

| | |
|---|---|
| 어디에 | 애플리케이션 로그 (`ExportFileService` · `ExportSheetService`) |
| 무엇을 | 형식 · 시점 · 단위(카드문구/어르신묶음/어르신표) · 대상 ID · 문구·항목 수 · 검토 안내 여부 |
| 남기지 않는 것 | **파일 내용과 문구 본문.** 카드·문구 쪽과 같은 이유다 |

**테이블을 만들지 않는다.** 복사(`copied_at`)가 컬럼인 이유는 화면이 "복사됨" 표시를 그리기 때문인데,
다운로드 이력을 보여 주는 화면은 Manyfast에 없다. 화면 없이 스키마부터 만들면 무엇을 담을지 추측하게 된다.

**`copied_at`을 건드리지 않는다.** 내려받기는 복사가 아니다. 파일을 받아 두고 붙여넣지 않을 수도 있고,
그것을 복사로 세면 "이 문구가 실제로 쓰였는가"라는 질문에 더 이상 답할 수 없다.

### 무엇이 나가는 글자인가

**화면에서 복사되는 것과 같다.** 직원이 고친 문구가 있으면 그것이다(`text = editedText ?? generatedText`).

**저장하지 않은 편집은 화면이 막는다.** 서버는 편집 중인지 알 수 없다. 복사와 똑같이 막지 않으면
화면에 보이는 글자와 파일 속 글자가 갈린다.

검토 안내(`reviewNotice`)는 파일에도 함께 들어간다. 안내가 붙은 문구를 내려받는 것 자체는 막지 않는다 —
단건·묶음 복사와 같은 이유다. 막는 것은 담을 문구 자체가 없을 때뿐이다.

### 규칙

| 규칙 | 결과 |
|---|---|
| `format`이 지원 목록에 없음 | `400` — `VALIDATION_FAILED`, `fields[0].field = format` |
| `phraseType`이 정의되지 않은 값 | `400` — `VALIDATION_FAILED`, `fields[0].field = phraseType` |
| 문구가 없음 | `404` — `EXPORT_PHRASE_NOT_FOUND` |
| 어르신이 목록에 없음 | `404` — `CARE_RECIPIENT_NOT_FOUND` |
| 내려받을 문구가 아직 없음 | `409` — `EXPORT_PHRASE_EMPTY` |
| 묶음에 담을 문구가 없음 | `409` — `EXPORT_BUNDLE_EMPTY` |

`format`과 `phraseType`을 **열거형 파라미터로 직접 받지 않는다.** 그러면 정의되지 않은 값이
`MethodArgumentTypeMismatchException`으로 새어 나가 공통 오류 형태를 벗어나고, 화면은 무엇을 고쳐야
하는지 모르는 오류를 받는다.

## 어르신 당일 표 내려받기

`GET /api/care-recipients/{careRecipientId}/export-sheet?date=2026-08-14`

**단위가 문구가 아니다.** 행은 **카드 한 장**이고, 열 가운데 담당·기한·처리 상태는 `task`에서 온다.
문구 하나에서 나오는 값이 아니라 경로도 형식도 문구 쪽과 나눠 뒀다. `date`를 생략하면 오늘이다.

응답은 `200 OK`와 `.xlsx` 바이트다.
(`application/vnd.openxmlformats-officedocument.spreadsheetml.sheet`)
**`format`을 받지 않는다.** 표는 한 형식뿐이라 고를 것이 없고, 열어 두면 "표를 텍스트로" 같은 요청이
만들어진다.

### 열

`ExportSheet.COLUMNS`의 순서가 파일의 열 순서다.

| 열 | 어디서 | 비어 있을 수 있나 |
|---|---|---|
| 어르신 | `care_recipient.name` | 아니다 |
| 시각 | `handover_card.observed_at`의 `HH:mm` | **그렇다.** 원문에서 뽑지 못하면 빈 칸 |
| 상태 변화 | `handover_card.status_change` | 그렇다 |
| 조치 | `handover_card.action_taken` | 그렇다 |
| 담당 | `task.assignee_name` → 없으면 `task.assignee_job_role` | 아니다. 없으면 `미배정` |
| 기한 | `task.due_time`의 `HH:mm` | **업무가 없으면 빈 칸** |
| 처리 상태 | `task.status`의 라벨(`미처리` · `완료`) | **업무가 없으면 빈 칸** |
| 근거 원문 | `handover_card.evidence_text` | 아니다 |

**"상태"를 한 열로 두지 않는다.** 상태 변화는 어르신의 몸 이야기이고 처리 상태는 업무가 닫혔는지다.
한 열에 섞으면 표를 정렬했을 때 서로 다른 두 가지가 같은 기준으로 줄을 선다.

**어르신 열을 행마다 둔다.** 표 하나는 어르신 한 명이지만, 여러 어르신의 표를 한 파일에 모아 붙이는
것이 이 형식을 쓰는 이유 가운데 하나다.

### 후속 업무가 없는 항목

담당은 `미배정`이고 **기한과 처리 상태는 빈 칸이다.** 없는 업무에는 기한도 상태도 없다.

**카드의 담당 직종 제안값(`suggested_job_role`)을 담당으로 적지 않는다.** AI가 제안했을 뿐 사람이
배정한 적이 없는 값이고, 표의 담당 칸에 적히는 순간 배정된 것으로 읽힌다. 비어 있다는 사실 자체가
"아직 아무도 맡지 않았다"는 정보다.

카드 한 장에 업무는 하나다. (`TaskRepository.existsByHandoverCardId`)

### 무엇이 들어가고 어떤 순서인가

| 규칙 | 근거 |
|---|---|
| 그날 만들어진 **검토 완료 카드만** 넣는다 | 묶음과 같은 기준 (`F-GUSOFG` dataSpec) |
| **안전 관련 항목이 먼저**, 그다음 **관찰 시각 순** | 묶음과 같은 기준 (`F-GUSOFG` action) |
| 같은 시각이거나 관찰 시각이 없으면 카드가 만들어진 순서 | 구현 |
| 날짜 기준은 **카드의 생성 시각** | 관찰 시각은 비어 있을 수 있어 기준으로 쓸 수 없다 |

거르는 기준을 묶음과 똑같이 맞춘다. 같은 화면에서 내려받는 두 파일이 서로 다른 카드를 담으면,
파일만 받은 사람은 어느 쪽이 그날의 전부인지 알 수 없다.

### 규칙

| 규칙 | 결과 |
|---|---|
| 어르신이 목록에 없음 | `404` — `CARE_RECIPIENT_NOT_FOUND` |
| 그날 담을 항목이 없음 | `409` — `EXPORT_SHEET_EMPTY` |

파일 이름은 `이어봄_인계표_김말순_2026-08-14.xlsx`다. 규칙은 문구 파일과 같다.
저장하는 것도 없다 — 형식과 시점, 몇 줄이었는지만 로그로 남는다.

## 이 API가 하지 않는 것

| 항목 | 어디서 |
|---|---|
| 보호자 자동 발송 · 보호자용 계정 | **없다.** MVP 범위 밖 |
| 기존 ERP 연동 · 대체 | **없다.** MVP 범위 밖 |
| 카드를 고친 뒤 문구 **재생성** | **없다.** 바뀐 사실을 안내만 하고, 고치는 것은 수정 API다 |
| 문구 수정 이력 열람 · 되돌리기 | **없다.** 카드 쪽과 같은 이유 |
| 묶음 저장 · 묶음을 LLM으로 다시 다듬기 | **없다.** 이어 붙이기만 한다 |
| 문구 삭제 | 없다. 복사하지 않으면 된다 |
| 내려받은 **파일 보관** · 다운로드 이력 조회 | **없다.** 형식과 시점만 로그로 남는다 |
| 특정 ERP 서식·템플릿에 맞춘 파일 | **없다.** 그 서식을 본 적이 없다 (`F-GUSOFG` rules) |
| `.hwp` · `.pdf` 출력 | **없다.** Manyfast에 없다. 필요해지면 `action`을 먼저 고친다 |
| 표에서 업무를 만들거나 담당을 바꾸기 | **없다.** 표는 읽기다. 배정은 [`task-api.md`](task-api.md) |

**문구 생성 · 수정 · 복사 이벤트**는 카드 쪽과 같은 이유로 별도 테이블 없이 애플리케이션 로그로 남긴다.
(`ExportPhraseService` · `ExportBundleService`) **문구 내용은 로그에 남기지 않는다.** 어르신의 상태
이야기가 로그 파일로 새어 나갈 이유가 없다. 대신 몇 개가 검토 안내를 달고 나갔는지를 남긴다.
"AI 문구를 그대로 쓸 수 있었는지"를 나중에 물을 수 있는 흔적이다.

**생성 단위가 카드 한 장인 것은 Manyfast에 명시돼 있다.** (`F-GUSOFG` action, `v0.3-plan-0813`)
유저플로우 "새 플로우 3"의 진입점이 카드 상세(n21)와 업무 상세(n34)이고, 문구를 만들 수 있는지 판정하는
`exportAllowed`도 카드마다 붙는다. 어르신 단위로 필요한 것은 **생성이 아니라 복사**이고, 그건
저장하지 않는 묶음으로 푼다. (위 [`GET .../export-bundles`](#get-apicare-recipientscarerecipientidexport-bundles))

## DB

`export_phrase` 테이블 하나다. `(handover_card_id, phrase_type)`에 유일 제약(`uk_export_phrase_card_type`)이
걸려 있다. 카드 한 장은 유형별로 문구를 하나씩만 갖는다.

`generated_text`와 `edited_text`를 **따로 둔다.** 한 칸에 덮어쓰면 직원이 무엇을 고쳤는지, 원래 AI가
뭐라고 했는지 더 이상 말할 수 없다.

근거 원문은 이 테이블에 복사해 두지 않는다. 카드가 들고 있고, 복사해 두면 카드를 고쳤을 때 두 값이
조용히 갈라진다.

`verified_at`은 **문구를 카드와 대조한 시점**이다. 만들 때와 고칠 때만 움직이고 복사할 때는 움직이지
않는다. 이 값과 `handover_card.updated_at`을 견줘 "만든 뒤 카드가 바뀌었는지"를 읽는 시점에 말한다.
값이 없는 옛 행은 `created_at`을 기준으로 본다 — `ddl-auto: update`로 굴러가는 로컬 DB에 값이 있는 행을
두고 `NOT NULL` 컬럼을 밀어 넣으면 기동부터 깨지므로 `NULL`을 허용한다.

**묶음에는 테이블도 컬럼도 없다.** 조회 시점에 만들고, 복사 기록은 묶음에 들어간 각 행의 `copied_at`에
남는다. 그래서 "이 묶음이 언제 복사됐는가"는 묶은 문구들의 `copied_at`으로만 말할 수 있고, 그것으로
충분하다. 필요한 것은 "이 문구가 실제로 쓰였는가"다.

## 실호출 확인

**스키마가 실제로 걸리는지, 모델이 카드에 없는 값을 지어내지 않는지는 stub으로 확인할 수 없다.**
`ExportPhraseSchema`가 잘못 생겼어도 stub 테스트는 전부 통과한다.

```bash
cd apps/api
LLM_API_KEY=... ./gradlew llmLiveTest     # 문구 생성 2회 (구조화 2회와 함께 돈다)
```

`OpenAiExportPhraseLiveTest`가 보는 것은 세 가지다. 두 문구가 함께 오는지, 같은 문장을 돌려 쓰지 않는지,
그리고 만들어진 문구가 `ExportPhraseVerifier` 판정을 그냥 통과하는지다. 마지막이 핵심이다 —
**체온을 재지 않은 카드에서 숫자가 나오면 그게 지어낸 것**이고, 그건 실호출에서만 드러난다.

`./gradlew build`에는 포함되지 않는다. 자세한 건 [`docs/development.md`](../development.md#llm-실호출-확인)에 있다.
