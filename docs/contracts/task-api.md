# task API

인계 카드의 **다음 행동**을 담당자와 기한이 있는 **후속 업무**로 바꾸고 완료까지 닫는다.

- Manyfast: `R-VZCOLM` 후속 업무 연결 및 처리 확인 / `F-IVFNPC` 후속 업무 배정 및 완료 처리
- 기준 버전: `v0.1-core-flow`
- 관련 화면: 유저플로우 "새 플로우 3" — n26 다음 행동 후속 업무 지정 → n27 배정 화면(n28 AI 제안값) → n29 · n30 → n34 업무 상세 → n35 대리 완료 → n36 · n37

> **당일 목록**(대시보드 · 하원 미처리 브리핑)은 Manyfast 기준 항목이 달라서
> [아래 절](#당일-목록--대시보드와-하원-미처리-브리핑)에 따로 적는다. 경로가 `/api/tasks` 아래라 같은 파일에 둔다.

> 제품이 **왜** 이렇게 동작하는지는 Manyfast가 기준이다. 여기에는 **JSON이 어떻게 생겼는지**만 적는다.

---

## 흐름

```
PUT   /api/handover-cards/{id}              카드를 검토하며 다음 행동·제안 직종·제안 기한을 확정 (handover-card-schema.md)
      ↓                                     이 값이 배정 화면의 프리필이 된다 (n28)
POST  /api/handover-cards/{cardId}/tasks    미처리 업무 생성 (n29)
      ↓
GET   /api/tasks/{taskId}                   업무 상세 (n34)
PATCH /api/tasks/{taskId}/complete          완료 처리 · 대리 완료 (n35)
```

**보내는 엔드포인트는 없다.** 알림·푸시는 MVP 범위 밖이다. 업무는 화면에서 확인하고 화면에서 닫는다.

## 기한이 왜 시각인가

이 API에서 가장 많은 규칙이 붙어 있는 값이 기한이다. 이유는 도메인 하나에서 나온다 —
**주야간보호는 어르신이 당일 귀가한다.** 그날 안에 닫히지 않은 업무는 다음 날로 넘어가는 것이 아니라
사실상 사라진다. 이 제품에는 지연 재알림도 다음 교대 자동 승계도 없기 때문이다. (`F-IVFNPC` rules)

| 규칙 | 어디서 막는가 |
|---|---|
| 날짜 단위 기한을 쓰지 않는다 | 형태. 기한을 `HH:MM` 으로만 받는다 |
| 익일 기한을 쓰지 않는다 | 형태. 날짜를 담을 자리가 없다 |
| 기본 상한은 **당일 하원 시각** | `DueTimePolicy`. 넘으면 `400` |
| 미완료 업무를 다음 날로 넘기지 않는다 | **아무것도 하지 않는다.** 승계 작업이 없다 |

앞의 둘을 규칙이 아니라 **형태로** 막는 것이 중요하다. DB 컬럼이 `TIME`이고 요청·응답이 `HH:MM`이라
날짜가 섞인 값은 본문을 읽는 단계에서 이미 걸린다. 검사로 막으면 검사를 빠뜨린 경로가 생긴다.

**이른 시각은 막지 않는다.** 이미 지난 시각으로 들어오는 업무는 늦게 발견된 일이고, 그런 업무야말로
미처리로 떠 있어야 한다. 막으면 기록 자체가 남지 않는다.

### 하원 시각

`ieobom.facility.dismissal-time`, 기본값 `18:00`. 환경변수 `FACILITY_DISMISSAL_TIME` 으로 덮는다.

**시설마다 다른 값인데 지금은 하나로 둔다.** 시설 설정 화면과 시설 엔티티가 아직 없어서, 지금 시설별
값을 만들면 화면 없이 스키마부터 추측하게 된다. 필요해지면 별도 Issue다. ([`#13`](https://github.com/ieobom-team/ieobom/issues/13))

`18:00` 은 Manyfast에 없는 값이라 구현에서 정했다. YAML에 직접 적을 때는 **따옴표로 감싼다** —
따옴표 없는 `18:00` 을 YAML은 시각이 아니라 60진수 정수(`1080`)로 읽는다.

## 상태는 두 값뿐이다

| 값 | 표시 |
|---|---|
| `PENDING` | 미처리 |
| `DONE` | 완료 |

**진행 중·접수·확인 같은 중간 상태를 추가하지 않는다.** (`F-IVFNPC` rules) 상태를 늘리면 "누가 무엇을
했는지"가 아니라 "상태가 무엇인지"를 관리하게 되고, 하원 미처리 브리핑이 봐야 하는 "아직 안 닫힌 것"의
경계가 흐려진다.

**미처리로 되돌리는 동작은 없다.** Manyfast에 없다. 그래서 완료 엔드포인트는 상태를 요청으로 받지 않고
한 방향만 한다.

## `POST /api/handover-cards/{cardId}/tasks`

카드의 다음 행동을 후속 업무로 만든다. (`F-IVFNPC` action)

```json
{
  "content": "저녁 식사량 확인",
  "assigneeJobRole": "NURSE_AIDE",
  "assigneeName": "박간호",
  "dueTime": "17:30"
}
```

### 응답 — `201 Created`

```json
{
  "id": 4,
  "handoverCardId": 31,
  "careRecipientId": 1,
  "careRecipientName": "김말순",
  "content": "저녁 식사량 확인",
  "assigneeJobRole": "NURSE_AIDE",
  "assigneeJobRoleLabel": "간호조무사",
  "assigneeName": "박간호",
  "dueTime": "17:30",
  "status": "PENDING",
  "statusLabel": "미처리",
  "delegated": false,
  "completedAt": null,
  "completedByName": null,
  "createdAt": "2026-08-12T14:02:11.402"
}
```

이 모양이 **업무 API가 공유하는 모양**이다. 상세 조회와 완료 처리도 같은 것을 돌려준다.
담당자 또는 담당 직종 · 기한 · 상태는 언제나 함께 나간다. 화면이 셋을 같이 보여 주기 때문이다. (`F-IVFNPC` display)

### 세 값은 화면이 프리필한 뒤 직원이 확정한다

배정 화면은 빈 입력이 아니라 **AI 제안값이 채워진 상태**로 열린다. (`F-IVFNPC` display, 유저플로우 n28)
그 값은 카드가 이미 들고 있다.

| 요청 | 프리필 출처 (카드 응답) |
|---|---|
| `content` | `nextAction` |
| `assigneeJobRole` | `suggestedJobRole` |
| `dueTime` | `suggestedDueTime` |

**제안값을 내려주는 엔드포인트를 따로 두지 않는다.** 카드 상세(n21)에서 배정 화면으로 넘어가므로
화면은 이미 카드를 들고 있고, 같은 값을 두 곳에서 내려주면 둘이 갈라진다.

**서버가 빈 칸을 카드 값으로 메우지 않는다.** 그러면 "직원이 그대로 확정한 것"과 "화면이 프리필에 실패해
빈 채로 보낸 것"이 요청에서 똑같이 보인다. 확정은 사람이 하는 동작이다.

### 규칙

| 규칙 | 결과 |
|---|---|
| 카드가 없음 | `404` — `HANDOVER_CARD_NOT_FOUND` |
| `content` 가 비었거나 500자 초과 | `400` — `VALIDATION_FAILED` |
| **담당 직종도 담당자 이름도 없음** | `400` — `VALIDATION_FAILED`, 두 항목을 **함께** 지목 |
| `dueTime` 이 없음 | `400` — `VALIDATION_FAILED` |
| `dueTime` 에 날짜가 섞여 있거나 `HH:MM` 이 아님 | `400` — `VALIDATION_FAILED` |
| `dueTime` 이 **하원 시각을 넘음** | `400` — `VALIDATION_FAILED`, 상한 시각을 문장에 담아 돌려준다 |
| 카드에 **다음 행동이 없음** | `409` — `CARD_NEXT_ACTION_MISSING` |
| 카드가 **대상 어르신을 가리지 못함** | `409` — `CARE_RECIPIENT_NOT_RESOLVED` |
| 이 카드에서 **이미 업무를 만들었음** | `409` — `TASK_ALREADY_CREATED` |

**담당은 직종과 이름 중 하나면 된다.** (`F-IVFNPC` exceptions — "담당자 또는 담당 직종") 수행자가 앱을
쓰지 않는 직종이면 사람을 특정하지 않고 직종으로만 배정하는 것이 현장의 기본 경로다. 둘 다 없을 때
**두 항목을 함께 지목하는** 이유는, 어느 한쪽만 가리키면 화면이 엉뚱한 칸에 안내를 붙이기 때문이다.

`assigneeJobRole` 선택지는 **PRD 5개 역할**로 한정한다. (`JobRole`) 목록에 없는 직종을 새로 만들지 않는다.
기능회복훈련 인력(물리치료사·작업치료사) 포함 여부는 Manyfast `F-IVFNPC` rules에 **미결 질문으로 열려**
있다. 포함하기로 정해지면 PRD 역할 목록을 먼저 고친 뒤 `JobRole` 에 반영한다.

### 검토 완료를 요구하지 않는다

문구 생성(`POST /api/handover-cards/{id}/exports`)과 갈리는 지점이다.

| | 요구 조건 |
|---|---|
| 문구 생성 | **검토 완료** 카드만 |
| 업무 배정 | 검토 상태를 보지 않는다 |

Manyfast는 "**검토 가능한** 인계 카드와 다음 행동 항목이 존재해야 한다"고만 한다. (`F-IVFNPC` preconditions)
유저플로우에서도 카드 상세(n21)는 검토(n25)와 배정(n26) 두 갈래로 함께 열려 있다. 무엇보다 **문구는
보호자에게 나가지만 업무는 내부에서 닫힌다.** 검토를 기다리게 하면 하원 전에 해야 할 확인이 밀린다.

**대상 어르신은 막는다.** 누구의 일인지 모르는 업무는 담당자가 받아도 수행할 수 없고, 완료 확인은 더 못 한다.

### 카드 한 장에 업무 하나

`(handover_card_id)` 에 유일 제약을 걸지 않고 서버가 본다. 다음 행동이 카드당 한 칸이므로 업무도 하나다.

**Manyfast에 없는 결정이라 구현에서 정했다.** 열어 두면 화면을 두 번 눌렀다는 이유로 같은 업무가 두 개
생기고, 하원 브리핑에서 둘 다 미처리로 뜬다. 다음 행동 하나에 실제 행동이 둘 섞여 있는 경우가 현장에서
문제가 되면 `propose-change` 로 올린다. **거는 쪽이 푸는 쪽보다 되돌리기 쉽다** — 제한을 풀 때는 코드만
고치면 되지만, 열어 두었다가 막을 때는 이미 쌓인 중복을 사람이 정리해야 한다.

## `PATCH /api/tasks/{taskId}/complete`

완료로 닫는다. (`F-IVFNPC` action · outcome)

```json
{ "completedByName": "이복지" }
```

### 응답 — `200 OK`

```json
{
  "alreadyCompleted": false,
  "notice": null,
  "task": {
    "id": 4,
    "status": "DONE",
    "statusLabel": "완료",
    "delegated": true,
    "completedAt": "2026-08-12T16:41:02.881",
    "completedByName": "이복지",
    "...": "위와 같은 모양"
  }
}
```

**받는 것은 완료를 확인한 사람 하나다.** 상태를 요청으로 받지 않는다. 상태가 두 값뿐이고 이 엔드포인트가
그중 한 방향만 하기 때문이다.

### 대리 완료

**확인자가 담당자와 달라도 된다.** (`F-IVFNPC` permissions) 이 제품은 수행자에게 앱 설치를 요구하지
않는 것을 전제로 한다. 운전원이 처리했다고 말하면 사회복지사나 센터장이 확인한 뒤 대신 눌러 루프를 닫는다.
그것을 막으면 앱을 쓰지 않는 직종의 업무는 영원히 미처리로 남는다.

`delegated` 는 저장하지 않고 판정한다 — **완료됐고, 담당자 이름이 있고, 확인자가 그와 다르면** 참이다.
직종만 배정된 업무는 사람 단위로 정해진 적이 없어 거짓이다. "대리 완료가 아니다"가 아니라 **"대리라고 말할
근거가 없다"** 에 가깝고, 화면은 확인자 이름을 그대로 보여 주면 된다.

### 이미 완료된 업무를 다시 완료하면

**오류가 아니다.** `200` 이고, `alreadyCompleted` 가 참이며, **아무것도 바뀌지 않는다.** (`F-IVFNPC` exceptions)

| | |
|---|---|
| 바뀌는 것 | **없다.** 완료 확인자도 완료 시각도 처음 값 그대로다 |
| `notice` | 중복 완료 안내 문장 (유저플로우 n37) |
| `task` | **지금 상태.** 먼저 완료한 사람과 그 시각이 들어 있다 |

두 사람이 같은 업무를 닫으러 오는 것은 이 현장에서 **정상**이다 — 수행자가 처리했다고 말하고, 관리자가
하원 브리핑에서 같은 항목을 본다. 그때 나중에 누른 사람으로 완료 확인자가 바뀌면 **실제로 확인한 사람의
기록이 사라진다.**

`409` 로 돌려주지 않는 이유는 화면이 보여 줘야 하는 것이 "실패했다"가 아니라 **지금 이 업무가 어떤
상태인지**이기 때문이다. 누가 언제 확인했는지를 보여 줘야 직원이 다시 물어보지 않고 넘어갈 수 있는데,
오류 응답(`ApiErrorResponse`)에는 그 값을 담을 자리가 없다.

| 규칙 | 결과 |
|---|---|
| 업무가 없음 | `404` — `TASK_NOT_FOUND` |
| `completedByName` 이 비었거나 공백뿐 | `400` — `VALIDATION_FAILED` |

**확인자 없이 닫을 수 없다.** 누가 확인했는지 없는 완료는 "다시 물어보지 않아도 되는가"에 답하지 못한다.
그 재확인을 없애는 것이 이 제품이 하려는 일이다.

## 당일 목록 — 대시보드와 하원 미처리 브리핑

여기서부터는 **당일 운영 현황 대시보드**(`F-HQTFLK`)가 읽는 목록이다.
Manyfast 기준 항목이 위와 다르다.

- Manyfast: `R-MFISQE` 현장 운영 현황 관리 / `F-HQTFLK` 당일 운영 현황 대시보드
- 기준 버전: `v0.3-plan-0813`
- 관련 화면: 유저플로우 **"AI 인계 도구 내비게이션 맵"** — n5 관리자 선택 → n42 관리자 대시보드(n43 당일 인계·업무 현황)
  → n48 브리핑 선택 → n44 하원 미처리 브리핑(n45 미처리 건수·목록)

> **이 절만 번호 기준이 다르다.** 이 문서의 위쪽 절(배정·완료)은 아직 유저플로우 "새 플로우 3" 번호를 쓴다.
> 두 플로우에서 같은 번호가 다른 화면을 가리키므로(예: n42 는 "새 플로우 3"에서 문구 수정 후 복사,
> 내비게이션 맵에서 관리자 대시보드) 번호와 화면 이름을 항상 함께 읽는다.

```
GET /api/tasks?date=                  당일 업무. 미처리·완료를 나눠서 (n42 · n43)
GET /api/tasks/pending-briefing?date= 그날 아직 안 닫힌 것만 (n44 · n45)
```

`date` 를 생략하면 오늘이다. 카드 목록(`GET /api/handover-cards`)과 같다.

### 인계와 업무를 한 응답으로 합치지 않는다

대시보드는 **당일 인계 · 미처리 · 완료** 세 영역을 그리는데, 인계는 이미 있는 카드 목록 API 를 그대로 쓴다.
합쳐서 한 번에 내려주지 않는 이유는 Manyfast 의 예외 규칙 때문이다 —
**"일부 목록 조회에 실패하면 성공한 정보와 실패한 영역을 구분해 표시한다."** (`F-HQTFLK` exceptions)

한 응답으로 묶으면 요청이 하나라 성공 아니면 실패뿐이고, 인계는 받았는데 업무를 못 받은 상태를
화면이 표현할 자리가 사라진다. 요청을 둘로 두면 화면이 영역별로 실패를 그린다.

### 당일의 기준은 **생성 시점**이다

`createdAt` 으로 자른다. (`F-HQTFLK` dataSpec) 기한으로 자르지 않는 이유는 형태에서 나온다 —
이 API 의 기한은 날짜가 없는 `HH:MM` 이라 "어느 날의 17:30 인가"를 물을 수가 없다.

| | |
|---|---|
| 오늘 만든 업무 | 오늘 목록에 있다 |
| **어제 만들어 아직 미처리인 업무** | **오늘 목록에 없다.** 어제로 물으면 그때는 보인다 |

두 번째 줄이 이 제품의 실제 동작이다. 당일만 보는 것이 명세이고 (`F-HQTFLK` rules) 다음 교대 자동
승계도 없으므로 (`F-IVFNPC` rules), 그 업무는 **어느 화면에도 뜨지 않는다.** 숨기는 것이 아니라
넘겨받는 장치가 없는 것이고, 현장에서 문제가 되면 `propose-change` 로 올릴 지점이다.

### `GET /api/tasks`

```json
{
  "date": "2026-08-13",
  "pending": [{ "id": 4, "...": "업무 하나. 위 201 과 같은 모양" }],
  "done": [{ "id": 3, "...": "같은 모양" }],
  "pendingCount": 1,
  "doneCount": 1
}
```

| 배열 | 정렬 | 왜 |
|---|---|---|
| `pending` | 기한 오름차순 | 하원 전에 무엇부터 확인해야 하는지가 그대로 순서다 |
| `done` | 완료 시각 내림차순 | 관리자가 묻는 것은 "무엇이 처리됐는가"이고 답은 최근에 있다 |

같은 값이면 `id` 순으로 고정한다. 정렬은 DB 가 아니라 **자바에서** 한다. 카드 목록과 같은 방침이다.

**상태 필터 파라미터를 두지 않는다.** 하루치가 어르신 20~30명 규모라 응답이 작고, 대시보드는 미처리와
완료를 동시에 그린다. 필터를 두면 화면마다 어떤 값을 넣었는지에 따라 "아직 안 닫힌 것"의 경계가 갈린다.

**`pendingCount` 는 배열 길이와 별개로 담는다.** 화면이 목록을 잘라 보여 주더라도 숫자는 줄면 안 되기
때문이다. **화면은 이 값을 그대로 표시한다** — 하원 미처리 브리핑은 목록과 별도로 건수를 세워 보여 주고
(`R-MFISQE` 수락기준 "하원 시점에 오늘 미처리로 남은 업무의 건수를 숫자로 확인할 수 있다", 유저플로우
n45 미처리 건수·목록), 대시보드 미처리 영역에도 같은 숫자를 붙인다. 화면이 배열 길이를 세지 않는다.

### `GET /api/tasks/pending-briefing`

```json
{
  "date": "2026-08-13",
  "pending": [{ "id": 4, "...": "같은 모양" }],
  "pendingCount": 1
}
```

**완료를 담을 자리가 없다.** 위 응답을 재사용하면서 `done` 을 비우면 그날 완료된 업무가 실제로 있어도
`doneCount` 가 0 으로 나가 응답이 거짓말을 한다. 브리핑이 답하는 질문은 하나뿐이다 —
**아직 안 닫힌 것이 무엇인가.**

**대시보드와 같은 데이터를 보면서도 엔드포인트를 나눈 이유는 로그다.** Manyfast 는 대시보드 조회와
브리핑 확인을 **서로 다른 이벤트**로 남기라고 한다. (`F-HQTFLK` outcome) 같은 호출을 두 화면이 함께
쓰면 로그에서 둘을 가를 수 없고, "현황을 훑어봤다"와 "하원 전에 남은 것을 실제로 폈다"는 다른 행동이다.

**브리핑을 연 것을 확인으로 본다.** "확인했음" 버튼을 따로 두지 않는다. 이 화면은 누락을 막아 준다고
약속하지 않고 남은 것을 보여 주는 데서 멈추는데, 확인 버튼은 그것을 닫았다는 느낌으로 바꾼다.

### 경로 두 개가 같은 깊이다

`/api/tasks/pending-briefing` 과 `/api/tasks/{taskId}` 는 깊이가 같다. Spring 이 경로 변수보다
**리터럴을 먼저** 맞추므로 동작하지만, 그것은 프레임워크의 매칭 규칙에 기대는 일이다. 우선순위가 깨지면
브리핑은 오류가 아니라 **`taskId` 파싱 실패로 조용히 `400`** 이 된다. `TaskListApiTest` 가 두 경로가
각자에게 가는 것을 고정한다.

## 이 API가 하지 않는 것

| 항목 | 어디서 |
|---|---|
| 기간 조회 · 통계 리포트 | **없다.** 당일만 본다 (`F-HQTFLK` rules) |
| 지연 재알림 | **없다.** MVP 범위 밖 |
| 다음 교대 자동 승계 | **없다.** MVP 범위 밖. 승계하는 코드가 없는 것으로 지킨다 |
| 알림 · 푸시 전송 | **없다.** 업무는 화면에서 확인하고 화면에서 닫는다 |
| 완료를 미처리로 되돌리기 | 없다. Manyfast에 없다 |
| 담당자 · 기한 **수정**, 업무 삭제 | 없다. Manyfast에 없다. 필요해지면 `propose-change` |

**자동 승계가 없다는 것을 어떻게 확인하는가** — 날짜를 넘기는 스케줄러도, 기한이 지난 업무를 건드리는
코드도 없다. 미처리 업무는 그대로 미처리로 남고, 하원 브리핑에서 사람이 본다. (`F-IVFNPC` rules)

**업무 생성 · 완료 처리 이벤트**는 카드 · 문구 쪽과 같은 이유로 별도 테이블 없이 애플리케이션 로그로
남긴다. (`TaskService`) **업무 내용과 담당자 · 확인자 이름은 로그에 남기지 않는다.** 어르신의 상태와 직원
이름이 로그 파일로 새어 나갈 이유가 없다. 대신 담당이 직종까지만 정해졌는지와 대리 완료였는지를 남긴다.

## DB

`task` 테이블 하나다. (`#21` 에서 만들어져 있다)

| 컬럼 | 왜 |
|---|---|
| `handover_card_id` | 업무가 어느 카드에서 나왔는지. `NOT NULL` — 근거 없는 업무를 만들지 않는다 |
| `due_time` | **`TIME`.** 날짜를 담을 자리가 없다. 익일 기한이 형태로 불가능해진다 |
| `status` | `PENDING` · `DONE` 두 값 |
| `completed_at` · `completed_by_name` | 완료 시점과 **확인자**. 담당자와 다를 수 있다 |
| `assignee_job_role` · `assignee_name` | 직종만, 사람만, 또는 둘 다. 하나는 반드시 있다 |

담당자 이름을 직원 테이블 참조가 아니라 문자열로 두는 이유는 **MVP에 계정·권한 모델이 없기** 때문이다.
진입 시 역할과 본인을 선택하는 식별을 쓰므로 가리킬 직원 행이 없다.

`delegated` 는 컬럼이 아니다. 담당자 이름과 확인자 이름에서 나오는 값이라 저장하면 두 값이 조용히 갈라진다.
