# notification API

후속 업무가 배정된 사실을 **담당 직원에게 앱 안에서 닿게 한다.**

- Manyfast: `R-VZCOLM` 후속 업무 연결 및 처리 확인 / `F-JIEOJO` 담당자 업무 배정 알림
- 기준 버전: `v38`
- 관련 화면: 유저플로우 "새 플로우 5" — 알림함 화면 → `배정 알림 목록` → `알림 항목 선택` → n40 후속 업무 상세

> 제품이 **왜** 이렇게 동작하는지는 Manyfast가 기준이다. 여기에는 **JSON이 어떻게 생겼는지**만 적는다.

---

## 흐름

```
POST  /api/handover-cards/{cardId}/tasks   업무 배정 → 새 담당자/직종에 알림 (task-api.md)
PATCH /api/tasks/{taskId}/assignee         담당자 변경 → 새 담당자(`TASK_ASSIGNED`) · 이전 담당자(`ASSIGNEE_CHANGED`)에 알림
PATCH /api/tasks/{taskId}/complete         대리 완료 → 담당자에게 알림
      ↓
GET   /api/notifications?staffCode=        내 알림함 (오늘 / 지난, 읽지 않은 개수)
PATCH /api/notifications/{id}/read         항목 하나를 읽음으로
```

**알림을 보내는 엔드포인트가 없다.** 화면이 "알림을 보내 줘"라고 부를 수 있으면 배정과 알림이 갈라져,
배정은 됐는데 알림은 안 간 상태를 화면이 만들 수 있다. 알림은 업무가 배정되거나 담당자가 바뀌거나 대리 완료될 때
**서버가 스스로 만든다.**

웹 푸시·기기 구독은 여기 없다. 별도 Feature다. (`F-QPWGNS`, [`#72`](https://github.com/ieobom-team/ieobom/issues/72))

## 유형은 세 가지뿐이다

| 값 | 표시 | 언제 |
|---|---|---|
| `TASK_ASSIGNED` | 새 업무 배정 | 나에게, 또는 내 직종에 업무가 배정됨 |
| `ASSIGNEE_CHANGED` | 담당 변경 | 내가 맡던 업무의 담당자가 다른 사람으로 바뀜 |
| `DELEGATED_COMPLETION` | 대리 완료 | 내가 담당인 업무를 다른 사람이 닫음 |

**값을 늘리지 않는 것이 요점이다.** (`F-JIEOJO` dataSpec) 기한 임박 재알림·미완료 반복 독촉·다음 교대
승계는 MVP 범위 밖이고, 그것들이 들어오는 자리가 바로 이 열거형이다. 유형이 늘면 알림함은 "무엇을 해야
하는지"를 알리는 화면에서 "무슨 일이 있었는지"를 나열하는 화면이 된다.

`ASSIGNEE_CHANGED` 는 관리자가 이미 있는 업무의 담당자를 변경할 때([`task-api.md`](task-api.md#patch-apitaskstaskidassignee)) **이전 담당자에게** 생성된다. (`F-JIEOJO` action) 이전 담당자가 없던 업무(직종만 배정)를 사람으로 바꿀 때는 알릴 이전 담당자가 없으므로 생성되지 않는다.

## 누구에게 만들어지는가

배정 요청의 담당 지정에 따라 갈린다. (`F-JIEOJO` action)

| 배정 | 알림 대상 |
|---|---|
| 담당자를 특정 (`assigneeName` + `assigneeStaffCode`) | **그 직원 한 명** |
| 직종만 (`assigneeJobRole`) | **그 직종에 등록된 직원 전원** |
| 직종만 + 그 직종에 직원 0명 | **없음.** 업무만 만들어진다 (`F-JIEOJO` exceptions) |
| 담당자 이름은 있는데 사번이 없음 | **없음.** 아래 참조 |

**직종 전원인 이유는 배정 화면의 담당자 기본값이 '직종만 배정'이기 때문이다.** 그 업무를 자기 일로 인식할
계기가 알림 말고는 없다. 한 명이 맡으면 나머지의 알림은 사라지지 않고, 목록에서 담당자 이름과 맡은 시각을
보여 주는 상태로 바뀐다. (아래 [갱신](#갱신하지-않는-것으로-갱신한다))

### 만들지 않는 두 경우

| 규칙 | 왜 |
|---|---|
| **배정한 사람 == 수신 직원** | 이미 아는 사실이다 (`F-JIEOJO` exceptions). 직종 전원 알림에서 배정자 본인의 알림함만 조용한 것이 정상이다 |
| **같은 업무 · 같은 수신자 · 같은 유형이 이미 있음** | 같은 사실을 두 번 알리는 것이다 (`F-JIEOJO` dataSpec) |

중복을 실제로 막는 것은 `uk_notification_task_recipient_type` **유일 제약**이다. 서비스 앞단의
`exists` 검사는 흔한 경우를 미리 걸러 제약 위반 예외를 로그에 쌓지 않으려는 것이고, 경합에서는 샌다.
담당 확정에서 조건부 UPDATE와 앞단 검사를 나눈 것과 같은 구조다.

### 대리 완료 알림

`Task#isDelegated` 하나로 가른다 — **완료됐고, 담당자 이름이 있고, 확인자가 그와 다르면** 참이다.

| 상황 | 알림 |
|---|---|
| 담당자가 있고 다른 사람이 닫음 | **간다.** 담당자에게 |
| 담당자 본인이 닫음 | 없다. "배정자==수신자면 만들지 않는다"의 완료 쪽 얼굴이다 |
| 직종에만 배정된 채 아무도 맡지 않고 닫힘 | 없다. **알릴 담당자가 없다** |
| 이미 완료된 업무를 다시 닫음 | 없다. 아무것도 바뀌지 않았으므로 알릴 사건도 없다 |

### 담당자 변경 알림

관리자가 담당자를 변경(`PATCH /api/tasks/{taskId}/assignee`)하면 양쪽에 알림이 만들어진다. (`F-JIEOJO` action)

| 대상 | 알림 유형 | 조건 |
|---|---|---|
| 새 담당자 | `TASK_ASSIGNED` | 새 담당자가 지정되었고 사번이 있음 (단, 변경자 != 새 담당자) |
| 이전 담당자 | `ASSIGNEE_CHANGED` | 이전 담당자가 있었고 새 담당자와 다름 (단, 변경자 != 이전 담당자) |

이전 담당자가 없었던 업무(직종만 배정)를 특정인으로 바꿀 때는 `ASSIGNEE_CHANGED` 는 만들지 않는다 — 알릴 이전 담당자가 없다.

## 배정 요청이 사번 두 칸을 받는다

알림 때문에 [`task-api.md`](task-api.md#post-apihandover-cardscardidtasks)의 배정 요청에
**선택 필드 두 개**가 늘었다.

```json
{
  "content": "저녁 식사량 확인",
  "assigneeJobRole": "NURSE_AIDE",
  "assigneeName": "최민재",
  "assigneeStaffCode": "ST-004",
  "assignedByStaffCode": "ST-001",
  "dueTime": "17:30"
}
```

| 칸 | 왜 필요한가 |
|---|---|
| `assigneeStaffCode` | 알림 수신자는 **직원 명단의 한 행**이어야 한다. 이름으로 되짚으면 동명이인에서 갈리고, 그때 조용히 안 보내면 배정 사실이 닿지 않는다 |
| `assignedByStaffCode` | 알림에 "배정한 사람"으로 표시되고 (`F-JIEOJO` display), 수신자와 같으면 만들지 않는 근거가 된다 |

**둘 다 선택이고, 없어도 업무는 그대로 만들어진다.** 명단에 없는 사번이 와도 `400`이 아니다.

> **알림용 칸이 업무 생성을 막으면 안 된다.** "알림이 실패해도 업무 생성은 성공한다"가 이 흐름의 확정
> 사항인데, 이 칸들을 필수로 검증하면 그 규칙이 **요청 검증 단계에서 뒤집힌다.** 사번이 없거나 틀리면
> 알림만 조용히 없다.

`assigneeName` 없이 `assigneeStaffCode` 만 보내면 담당자를 정한 것으로 보지 않으므로 무시된다.

### 담당자 이름만 있고 사번이 없으면 알림이 없다

화면이 아직 사번을 보내지 않는 경로가 여기 해당한다. **직종 전원으로 넓히지 않는다** — 사람이 이미 정해진
업무를 직종 전원에게 알리면 *내 일이 아닌 업무*가 여러 명의 알림함에 뜬다. 그것이 배정 사실이 한 명에게
안 닿는 것보다 나쁘다. 알림함은 "내가 할 일"이라는 약속을 지켜야 열어 볼 가치가 있다.

## `GET /api/notifications`

```
GET /api/notifications?staffCode=ST-004
```

### 응답 — `200 OK`

```json
{
  "staffCode": "ST-004",
  "unreadCount": 2,
  "today": [
    {
      "id": 9,
      "type": "TASK_ASSIGNED",
      "typeLabel": "새 업무 배정",
      "read": false,
      "actorName": "강태호",
      "safetyRelated": true,
      "createdAt": "2026-08-15T14:02:11.402",
      "readAt": null,
      "task": {
        "id": 4,
        "careRecipientName": "김말순",
        "content": "낙상 부위 확인",
        "dueTime": "17:30",
        "assigneeName": null,
        "claimable": true,
        "status": "PENDING",
        "...": "task-api.md 의 TaskResponse 와 같은 모양"
      }
    }
  ],
  "past": []
}
```

| 값 | 무엇 |
|---|---|
| `actorName` | 이 알림을 일으킨 사람. 배정 알림이면 **배정한 사람**, 대리 완료 알림이면 완료를 확인한 사람. 배정자를 보내지 않았으면 `null` |
| `safetyRelated` | 안전 관련 카드에서 나온 업무인지. 참이면 목록 위쪽에 온다 (`F-JIEOJO` display) |
| `task` | **업무를 통째로 중첩한다.** 아래 참조 |

### 갱신하지 않는 것으로 갱신한다

Manyfast는 **"직종 배정 알림은 다른 직원이 그 업무를 맡으면 누가 맡았는지 보여 주는 내용으로 갱신된다"**
고 한다. (`F-JIEOJO` action) 이 API는 **갱신할 문구를 저장하지 않는 것**으로 그것을 지킨다.

알림 행에는 어르신 이름도 업무 내용도 기한도 담당자도 없다. 전부 `task` 를 그때그때 읽어 내려준다.
그래서 **갱신에 실패할 수도 없다.**

| 화면이 묻는 것 | 어느 값으로 답하나 |
|---|---|
| '내가 처리할게요'를 그릴까 | `task.claimable` |
| 누가 이미 맡았나 | `task.assigneeName` · `task.claimedAt` |
| 이미 완료된 업무인가 | `task.status` (`F-JIEOJO` exceptions — 알림을 지우지 않고 완료를 함께 표시한다) |

문장을 만들어 저장했다면 업무가 바뀔 때마다 알림 행을 UPDATE 해야 하고, 한 번 빠뜨리면 알림함이
옛말을 한다.

### 오늘과 지난 것을 서버가 가른다

`createdAt` 이 오늘 자정 이후면 `today`, 아니면 `past` 다. 화면이 나누게 하지 않는 이유는 하루의 경계가
업무 목록·하원 브리핑과 **공유하는 규칙**이라, 한 곳에서 정해야 세 화면이 같은 하루를 보기 때문이다.

각 묶음 안의 순서는 **안전 관련 먼저, 그다음 최신순**이다. (`F-JIEOJO` display) 같은 시각이면 id
역순으로 갈라 순서를 고정한다 — 30초마다 다시 조회하는 화면이라 (`F-JIEOJO` rules) 같은 값에서
순서가 흔들리면 목록이 주기적으로 뒤집힌다.

### `unreadCount` 는 당일분만 센다

```
unreadCount == today 안에서 readAt 이 비어 있는 개수
```

**`past` 에 읽지 않은 알림이 아무리 많아도 배지에 들어가지 않는다.** (`F-JIEOJO` rules)

지난 알림이 **사라지지 않으면서** 배지에는 안 들어가는 것이 이 규칙의 요점이다. 사라지면 조회가 안 되고
(누적 보관이 명세다), 배지에 들어가면 어제 못 본 알림이 오늘 숫자로 남아 하원 미처리 브리핑의 "오늘
미처리 건수"와 어긋난다. 어제 것이 오늘 숫자에 얹히는 것은 범위 밖인 **다음 교대 자동 승계**와 화면에서
구분되지 않는다.

### 목록을 여는 것만으로는 읽음이 되지 않는다

이 엔드포인트는 **아무것도 바꾸지 않는다.** (`F-JIEOJO` rules) 읽음은 아래 하나뿐이다.

### 규칙

| 규칙 | 결과 |
|---|---|
| `staffCode` 가 없거나 공백뿐 | `400` — `VALIDATION_FAILED`, `staffCode` 지목 |
| 명단에 없는 사번 | `404` — `STAFF_NOT_FOUND` |
| 알림이 하나도 없음 | `200`, 빈 목록과 `unreadCount: 0` |

**사번을 쿼리로 받는다.** 인증이 없으므로 (`F-JIEOJO` permissions) 서버가 "너 누구냐"를 알 길이 화면이
보내는 값뿐이다. 계정 모델을 만들지 않는다는 원칙의 연장이고, 담당 확정이 사번을 받는 것과 같은 자리다.

`staffCode` 를 `required = false` 로 받고 직접 검사하는 이유는 **오류 응답 형태** 때문이다. Spring이
빠진 파라미터를 스스로 막으면 `ApiErrorResponse` 가 아닌 다른 모양이 나가고, 화면은 이 API에서만 다른
오류 형식을 다뤄야 한다.

## `PATCH /api/notifications/{id}/read`

```json
{ "staffCode": "ST-004" }
```

### 응답 — `200 OK`

위 목록 항목 하나와 **같은 모양**이다. `read` 가 참이고 `readAt` 이 채워져 있다.

### 항목 단위다

**목록을 여는 것도, 전체 읽음 버튼도 없다.** (`F-JIEOJO` rules) 눌러서 업무 상세로 들어간 것만 읽음이다.
전체 읽음이 있으면 배지를 0으로 만드는 것이 목적이 되고, 그 순간 알림함은 배정 사실을 전달하는 화면이
아니라 지워야 할 숫자가 된다.

화면은 이 호출과 함께 업무 상세로 이동한다. 두 동작을 한 요청으로 묶지 않는 이유는 이동이 화면에 이미
있는 `task.id` 로 되는 일이고 서버가 관여할 것이 아니기 때문이다.

### 이미 읽은 알림을 다시 눌러도

**오류가 아니다.** `200` 이고 **읽음 시각이 덮이지 않는다.**

읽음 시각이 답하는 질문은 "언제 알아챘는가"이고, 다시 눌렀다고 그 시점이 지금으로 옮겨 가면 배정에서
확인까지 걸린 시간을 물을 수 없게 된다. **그 값이 이 기능이 실제로 효과가 있었는지를 재는 유일한 숫자다.**

### 규칙

| 규칙 | 결과 |
|---|---|
| `staffCode` 가 비었거나 공백뿐 | `400` — `VALIDATION_FAILED` |
| 알림이 없음 | `404` — `NOTIFICATION_NOT_FOUND` |
| **다른 직원의 알림** | `404` — `NOTIFICATION_NOT_FOUND`. 바뀌는 것 없음 |
| 이미 읽음 | `200`, **바뀌는 것 없음** |

남의 알림을 `403` 이 아니라 `404` 로 두는 이유는 **이 제품에 권한 모델이 없기** 때문이다. 진입 시
역할과 본인을 고르는 식별뿐이라 인증된 주체가 없고, 거절의 근거는 요청자의 권한이 아니라 **그 사번의
알림 중에 그런 id가 없다**는 사실이다. 담당 확정의 직종 불일치를 `403` 이 아니라 `409` 로 둔 것과 같은
논리다. 계정 모델이 생기면 다시 볼 지점이다.

조회 질의에 사번을 함께 거는 것도 같은 이유다. id로만 찾은 뒤 자바에서 수신자를 비교하면, 그 비교를
빠뜨린 경로가 생기는 날 남의 알림이 읽음으로 바뀐다.

## 알림 생성이 업무 생성을 죽이지 않는다

**업무 생성이 알림 실패로 롤백되면 안 된다.** 방법이 세 개 겹쳐 있다.

| 겹 | 무엇을 막나 |
|---|---|
| `TaskService` 가 `ApplicationEvent` 만 발행 | 업무 패키지가 알림 패키지를 부르지 않는다. 의존은 알림 → 업무 한 방향 |
| `@TransactionalEventListener(AFTER_COMMIT)` | 알림 코드가 돌 때 업무는 **이미 커밋됐다.** 되돌릴 것이 없다 |
| `REQUIRES_NEW` + `try/catch` | 알림은 자기 트랜잭션에서 돈다. 예외는 잡아서 로그로만 남긴다 |

**같은 트랜잭션 안에서 `try/catch` 로는 지킬 수 없다.** JPA 예외 하나면 트랜잭션에 롤백 표시가 남아,
잡아 삼켜도 커밋 시점에 업무까지 함께 죽는다.

`try/catch` 가 세 번째로 필요한 이유는 따로 있다 — `afterCommit` 에서 던진 예외는 커밋을 되돌리지
못하지만 **호출자에게 전파되어** 배정 응답을 `500` 으로 만든다. 업무는 저장됐는데 화면은 실패로 보는
상태가 가장 나쁘다.

**비동기가 아니다.** 응답이 나가기 전에 동기로 돈다. 파일럿 규모에서 알림 몇 행을 넣는 비용이 배정 응답을
늦출 만하지 않고, 비동기로 두면 배정 직후 알림함을 열었을 때 아직 없는 경우가 생긴다.

## 웹 푸시 (`F-QPWGNS`, #72)

직원이 허용한 기기(안드로이드 크롬, PC 웹)에 한해 앱을 열고 있지 않아도 새 업무 배정을 알린다.

- **보조 채널**: 앱 내 알림 생성 시에만 함께 발송되며, 푸시 단독 발송은 없다.
- **프라이버시**: 푸시 본문에는 **어르신 실명, 증상, 투약, 낙상, 병원 일정, 인계 원문이 없다**. ("새 후속 업무가 배정되었습니다", 기한 시각까지만 담김)

### `GET /api/push-subscriptions/public-key`
VAPID 공개키를 조회한다. 프론트엔드가 브라우저 `PushManager.subscribe()` 호출 시 사용한다.

```json
{
  "publicKey": "BI..."
}
```

### `POST /api/push-subscriptions`
기기 구독을 등록하거나 직원을 재연결한다 (기기 단위 upsert).

```json
{
  "staffCode": "ST-004",
  "endpoint": "https://fcm.googleapis.com/fcm/send/...",
  "p256dh": "...",
  "auth": "..."
}
```
- 동일한 `endpoint`로 요청이 다시 오면 연결 직원(`staffCode`)과 키만 덮어쓴다.

### `DELETE /api/push-subscriptions`
기기 구독을 해제하거나 직원 연결을 끊는다.

```json
{
  "endpoint": "https://fcm.googleapis.com/fcm/send/..."
}
```

## 이 API가 하지 않는 것

| 항목 | 어디서 |
|---|---|
| 카카오 알림톡 · SMS | **없다.** MVP 범위 밖 |
| 기한 임박 재알림 · 미완료 반복 독촉 | **없다.** MVP 범위 밖. 보내는 코드가 없는 것으로 지킨다 |
| 다음 교대 자동 승계 | **없다.** MVP 범위 밖 |
| 전체 읽음 · 목록을 여는 것만으로 읽음 | 없다 (`F-JIEOJO` rules) |
| 알림 삭제 · 보관 기간 만료 | 없다. 기간 제한 없이 누적 보관한다 (`F-JIEOJO` rules) |
| SSE · WebSocket | **없다.** 화면이 30초마다 다시 조회한다 (`F-JIEOJO` rules) |
| 보호자에게 가는 알림 | 없다. 수신 대상은 직원 명단뿐이다 (`F-JIEOJO` permissions) |
| iOS 탭 사파리 푸시 | 지원하지 않음. 안드로이드 크롬 및 PC 웹 대상 |

**어르신 실명을 앱 내 알림에만 담는다.** 푸시 알림에는 실명을 넣지 않는다.

**알림 생성·읽음 이벤트**는 카드·업무 쪽과 같은 이유로 별도 테이블 없이 애플리케이션 로그로 남긴다.
**수신자 이름도 업무 내용도 남기지 않는다.** 남기는 것은 대상 수와 실제로 만들어진 수이고, 둘이 갈리는
건수 — 배정자 자신이라서, 또는 이미 있어서 건너뛴 것 — 가 나중에 물을 값이다. 알림함 조회는 30초마다
도는 호출이라 `DEBUG` 로만 남긴다.

## DB

`notification` 테이블 하나다.

| 컬럼 | 왜 |
|---|---|
| `recipient_staff_id` | 수신 직원. **`staff` 외래키다.** 업무의 담당자가 문자열인 것과 갈리는 지점 |
| `task_id` | 가리키는 업무. `NOT NULL` — 하나의 알림이 여러 업무를 가리키지 않는다 (`F-JIEOJO` dataSpec) |
| `type` | 세 값 (`VARCHAR(30)`) |
| `actor_name` | 알림을 일으킨 사람. 배정자 또는 완료 확인자. 비어 있을 수 있다 |
| `read_at` | 읽은 시각. 읽기 전까지 비어 있다 |
| `created_at` · `updated_at` | `BaseTimeEntity` 공통 |

수신자만 **외래키**인 이유는, 알림은 **받을 사람이 명단에 있어야만** 만들어지기 때문이다.
(`F-JIEOJO` preconditions) 업무는 앱을 쓰지 않는 직종에도 배정되므로 가리킬 직원 행이 없을 수 있지만,
받는 사람이 없는 알림은 조회될 길이 없다.

### 유일 제약

```sql
unique (task_id, recipient_staff_id, type)   -- uk_notification_task_recipient_type
```

같은 업무·같은 수신자·같은 유형을 두 번 만들지 않는다는 규칙(`F-JIEOJO` dataSpec)을 **DB가 지킨다.**
서비스의 `exists` 검사는 그 앞에서 흔한 경우를 걸러 낼 뿐이다.

### `task` 에 늘어난 컬럼

| 컬럼 | 왜 |
|---|---|
| `assignee_staff_code` (`VARCHAR(30)`) | 담당자의 사번. **알림을 누구에게 보낼지가 이 값으로 갈린다** |

담당자 이름을 문자열로 둔 결정을 뒤집지 않는다. 사번은 **알림을 보낼 수 있을 때만** 채워지는 보조 값이고,
비어 있어도 업무는 온전하다. 담당 확정(`PATCH /api/tasks/{id}/claim`)도 이름과 함께 이 값을 남긴다 —
직종에만 배정됐던 업무는 거기서 처음 사람이 붙고, 그 사람이 나중에 대리 완료 알림을 받을 수신자다.

### 직종 전원 알림의 행 수

직종에 등록된 **직원 수만큼** 행이 생긴다. 파일럿 규모(직종당 한 자릿수)를 전제한 구조이고 **상한이 없다.**
근거 있는 상한이 없어 지금 정하면 추측이 되고, 규모가 문제가 되면 그때가 `propose-change` 지점이다.

> **Flyway.** `V1__*.sql` 은 아직 없고 스키마는 `ddl-auto: update` 로 만들어진다.
> [`#19`](https://github.com/ieobom-team/ieobom/issues/19) 에서 첫 마이그레이션을 쓸 때
> **`notification` 테이블 전체와 유일 제약, 그리고 `task.assignee_staff_code` 컬럼이 빠지지 않아야
> 한다.**
